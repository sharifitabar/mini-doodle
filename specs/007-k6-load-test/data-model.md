# Phase 1 Data Model: Load-Test Dataset

**Feature**: `007-k6-load-test` | **Date**: 2026-10-18

This feature adds **no tables and no migration**. It populates the existing schema
(`users`, `calendars`, `time_slots`, `meetings`, `meeting_participants`) with a synthetic dataset
shaped to the spec's scale, and derives a handful of non-persisted concepts (run, flow, target,
verdict) that exist only in k6 and in dashboards.

---

## 1. Persisted entities (existing tables, synthetic rows)

### LoadUser → `users`

| Column | Value |
| --- | --- |
| `id` | reserved namespace, see §2 — `10000000-0000-4000-8000-` + `lpad(to_hex(n), 12, '0')` for `n = 1…1000` |
| `display_name` | `Load User {n}` |
| `created_at`, `updated_at` | database defaults |

Exactly 1000 rows. The demo user seeded by `DevDataSeeder` (`11111111-1111-1111-1111-111111111111`)
is untouched and coexists.

### LoadCalendar → `calendars`

One row per load user (`uq_calendars_user` enforces exactly one calendar per user):
`id = 20000000-0000-4000-8000-` + `lpad(to_hex(n), 12, '0')`, `user_id =` the matching load user.
Exactly 1000 rows.

### LoadTimeSlot → `time_slots`

The bulk of the dataset. Per user `n`, `slots(n) = 600 + (n × 37) mod 201`, i.e. **600…800 slots**
with the busiest users exactly at the 800 ceiling required by FR-007.

| Column | Value |
| --- | --- |
| `id` | `30000000-0000-4000-8000-` + `lpad(to_hex((n−1) × 1000 + i + 1), 12, '0')`, `i = 0…slots(n)−1` |
| `calendar_id` | that user's calendar |
| `start_at` | `T0 − (i + 1) × 45 minutes + (n mod 15) minutes` |
| `duration_minutes` | `30` |
| `status` | `FREE`, except the first `meetings(n)` slots (lowest `i`), which are `BUSY` |
| `slot_range` | generated by the database from `start_at` + `duration_minutes` |

`T0 = date_trunc('hour', now())` at seed time, captured once in the seeding transaction.

Total: **600,000 + Σ((n × 37) mod 201) ≈ 700,000 rows**.

### LoadMeeting → `meetings`

Per user `n`, `meetings(n) = (n × 13) mod 101`, i.e. **0…100 meetings**, never more than that
user's slot count (min 600). Placed on that user's slots with the smallest `i` (which are therefore
the `BUSY` ones — exactly mirroring what `POST /api/v1/slots/{id}/meeting` produces).

| Column | Value |
| --- | --- |
| `id` | `40000000-0000-4000-8000-` + `lpad(to_hex((n−1) × 1000 + i + 1), 12, '0')` |
| `slot_id` | the matching slot (`uq_meetings_slot` guarantees one meeting per slot) |
| `title` | `Load meeting {n}-{i}` (non-blank, ≤ 200 chars) |
| `description` | `Synthetic meeting for load-test user {n}` |
| `created_at`, `updated_at` | database defaults |

Total: **Σ((n × 13) mod 101) ≈ 50,000 rows**.

### LoadMeetingParticipant → `meeting_participants`

Two per meeting, so the dataset carries the same relational weight the API produces:

| Column | Value |
| --- | --- |
| `meeting_id` | the meeting |
| `position` | `0`, `1` |
| `name` | `Participant {position} of {n}` (≤ 100 chars) |
| `email` | `participant{position}.user{n}@loadtest.local` (≤ 254 chars) |

Total: **≈ 100,000 rows**. Present for honesty of shape; the measured flows never read them.

## 2. UUID namespace (the reset boundary)

The namespace is the contract that makes seeding idempotent and resetting safe.

| Range start (inclusive) | Range end (exclusive) | Entity |
| --- | --- | --- |
| `10000000-0000-4000-8000-000000000000` | `20000000-0000-4000-8000-000000000000` | load users |
| `20000000-0000-4000-8000-000000000000` | `30000000-0000-4000-8000-000000000000` | load calendars |
| `30000000-0000-4000-8000-000000000000` | `40000000-0000-4000-8000-000000000000` | load slots |
| `40000000-0000-4000-8000-000000000000` | `50000000-0000-4000-8000-000000000000` | load meetings |

PostgreSQL compares `uuid` byte-wise, so range predicates on the primary key use the index — unlike
a `LIKE` on a text cast. The demo user, any hand-made data, and the whole migration history sit
outside these ranges and are never touched by a reset.

## 3. Non-persisted concepts

| Concept | Where it lives | Definition |
| --- | --- | --- |
| **Run** | `TEST_ID` wide tag on every k6 series; the summary artifact filename | One execution: one seeded dataset, one steady-state window, one verdict. |
| **Flow** | `flow` tag on every k6 request metric (`availability` \| `manipulation`) | Which of the two request kinds a measurement belongs to. |
| **Read window** | `WINDOW_FROM` / `WINDOW_TO` passed to the generator | `[min(start_at), max(start_at) + 1 hour]` of the seeded slots — covers every user's whole history, ≈25 days, inside the 31-day `MAX_SPAN` limit. |
| **Target** | k6 `thresholds` | The five bounds in `contracts/load-scenario.md`. |
| **Verdict** | k6 exit code + summary artifact | `0` = every threshold held; `99` = at least one breached. |

## 4. Invariants

The seeder duplicates what the domain and the database would otherwise enforce together. Each
invariant below is asserted by `loadtest/sql/verify.sql` after seeding, and the ones marked
*DB-enforced* cannot be violated even by a buggy seeder — the insert fails.

| # | Invariant | Enforcement |
| --- | --- | --- |
| I1 | 1000 load users, each with exactly one calendar | *DB-enforced* (`uq_calendars_user`) + assertion |
| I2 | A user's slots never overlap | *DB-enforced* (`ex_slot_no_overlap` GiST exclusion) + assertion that the seed produced no error |
| I3 | Slot count per user is within 600…800, and at least one user is at exactly 800 | assertion |
| I4 | Meetings per user ≤ 100 and ≤ that user's slot count | assertion |
| I5 | Every meeting's slot is `BUSY` and no `BUSY` slot lacks a meeting | assertion (this is the state the booking use case leaves behind) |
| I6 | Every `BUSY` slot belongs to a slot-holding meeting; every meeting has ≥ 1 participant with a name or an email | *DB-enforced* (`ck_participant_present`) + assertion |
| I7 | All seeded slots are in the past, so the future is free for the manipulation flow | assertion |
| I8 | The database has fresh statistics before load starts | `ANALYZE` at the end of `seed.sql` |
| I9 | Re-running the seed changes nothing (same row counts, same shape) | assertion run twice + `ON CONFLICT DO NOTHING` |

**I8 is not cosmetic.** Without statistics on `time_slots` the planner can prefer a sequential scan
over the `(calendar_id, start_at)` index or the GiST range index, and the latency reported for the
availability flow would describe a planning accident rather than the service.

## 5. Seeding and reset semantics

**Seed** (`loadtest/sql/seed.sql`) — single transaction, four `INSERT … SELECT` statements driven by
`generate_series(1, 1000)`, deterministic UUID computation, `ON CONFLICT DO NOTHING` so a re-run is a
no-op, closing `ANALYZE users, calendars, time_slots, meetings, meeting_participants`. The script
reports elapsed time and row counts.

**Reset** (`loadtest/sql/reset.sql`) — order is load-bearing, and the `meetings` predicate must be
**ownership-based, not name-based**:

1. `DELETE FROM meetings WHERE slot_id IN (SELECT s.id FROM time_slots s JOIN calendars c ON
   c.id = s.calendar_id WHERE c.user_id >= '10000000-…' AND c.user_id < '20000000-…')`
   — participants go with them (`meeting_participants.meeting_id` is `ON DELETE CASCADE`).
2. `DELETE FROM users` in the user namespace → cascades to `calendars` → cascades to `time_slots`.
3. `ANALYZE` the affected tables so the next run starts from real statistics rather than the
   previous run's.

Why step 1 cannot simply use the `40000000-…` meeting namespace: `meetings.slot_id` is
`ON DELETE RESTRICT`, so deleting a slot that still has a meeting fails — and the meetings created
by *previous runs of the manipulation flow* are written by the application with random UUIDs, not
with namespace UUIDs. A namespace-scoped delete would therefore leave meetings behind and the
cascade in step 2 would abort with a foreign-key violation. This is the same failure mode
`JooqSlotRepository` had to handle for non-foreign-key delete failures.

Repeated delete/insert cycles leave dead tuples. That is acceptable for the harness's purpose, and
`quickstart.md` documents `docker compose down -v` as the clean-slate path when it matters.

## 6. Sizing

| Metric | Value |
| --- | --- |
| Rows inserted per seed | ≈ 851,000 (1,000 users + 1,000 calendars + ≈700,000 slots + ≈50,000 meetings + ≈100,000 participants) |
| On-disk footprint with indexes | ≈ 0.4–0.6 GB |
| Expected seed wall-clock | seconds to a couple of minutes on a laptop (one pass, no application round-trips) |
| Measured-window traffic | ≈ 55,000–60,000 requests, of which ≈ 2,800–3,000 are manipulation sequences |
